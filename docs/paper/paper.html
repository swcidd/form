Because the roles were held by one person, the value of separating them is not coordination but review: each role produced an artefact the others could check. Working method

Work moved through four branches: feat/* for features, dev as the integration branch, staging for what is about to be released, and master for what was released. Every feature arrived as a pull request with review comments on the lines that carried a decision, not on formatting. Every commit was required to be green on its own — formatter, analyzer and the full test suite before the commit was made — so that a bisect never lands on a broken tree.

Section 02Problem Statement

Strength training only works if the load goes up, and the load can only go up if the lifter knows what it was last time. That single fact is the whole problem: the numbers that matter are the ones nobody can remember.

The problem

Progressive overload — doing a little more than last time — is the mechanism by which training produces strength. It requires a comparison: this week's bench press against last week's. Most people training in a gym carry that comparison in their head, or in a notes app, or on a paper card that stays in the car. Memory is unreliable under fatigue, and a note that records “bench 3×8” without the weight cannot answer the only question the next set asks.

The apps that solve this tend to solve several other things at once. They ask for an account before showing a screen, sync to a cloud the user cannot inspect, fill the dashboard with step counts and calorie estimates, and add social surfaces that turn a training log into a feed. Each addition is another thing that can be wrong, another number that was invented rather than measured, and another reason the app needs a network to open.

Why it matters

  • Without a record there is no overload. A lifter who cannot see last week's weight either repeats it or guesses upward; both waste sessions.
  • Progress is invisible in the short term. A single session rarely feels easier; a month of volume does not feel different. Only a comparison makes the change visible, which is what keeps people training.
  • Trust is easy to lose. One fabricated figure — a personal record nobody earned, a duration nobody measured — teaches the user to distrust every other number on the screen.
  • Gyms have poor signal. A logging app that needs the network fails exactly where it is used.

Current challenges

Existing trackers are either heavy or thin. The heavy ones require an account and a cloud, which makes an offline demo impossible; the thin ones are note fields with a stopwatch, which cannot compute a record or a weekly comparison. Both leave the same gap: a fast log, a truthful summary, and a progress view derived from what was actually performed.

Target users

FORM is for the beginner-to-intermediate lifter training three or four times a week, who wants to log a session in under a minute and see an honest picture of the last month. It is also for the privacy-minded user who does not want an account to lift, and for the student who needs the app to work on a phone with no data plan. All three pull in the same direction: local first, account optional, no invented numbers.

Section 03Application Overview

FORM is a Flutter application for logging strength training and reading progress from the log. It ships empty, works offline, and every figure it prints can be traced back to a session the user recorded.

Repository: https://github.com/swcidd/form — public, with the full commit history, pull requests and reviewed changes.

What it is

The app has eleven screens. A first launch offers a welcome with three ways in: create an account, sign in, or continue offline as the device account. Behind that front door is a shell with five destinations — Home, Progress, Workout, Library and Profile — plus three screens reached from a session: the workout detail, the set logger and the summary.

A session is a plan: exercises, each with sets of reps and weight. The user ticks sets as they are performed, and the session finishes when the last set is ticked. Home shows the session to walk into next, the week's target and the most recent sessions. Progress derives records, volume and consistency from finished sessions only. The Library holds the user's rotation and a searchable catalogue of exercises, read from the public wger API when the device is online and from a bundled set when it is not.

How it works, in the order a user meets it

  1. Open. No session? The welcome. A session? The app, on the account that owns it.
  2. Home. “Up next” names today's session and how much of it is done; the week shows finished sessions against the goal; recent sessions show what happened.
  3. Log. Ticking the last planned set closes the session. Unticking one reopens it. Every tap writes through a repository to SQLite.
  4. See. The summary turns the session into volume, duration, sets, reps and — only if it really beat one — a record.
  5. Reflect. Progress ranks records by estimated one-rep max, compares this month's volume with last month's, and measures consistency over thirty days.
One rule, applied everywhere

Only finished sessions count, and inside them only completed sets. A set that was planned and never ticked is work nobody did; counting it would let a routine nobody performed move every number in the app.

Section 04Proposed Solution

The concept is one sentence long: the app remembers, so the user can progress. Everything below follows from taking that sentence literally — a memory that is durable, private and honest, and a view of it that answers the next question.

The idea

FORM treats the training log as the only source of truth. A session, its exercises and its sets are stored; every other number in the app is computed from them on read. Nothing is stored twice, so nothing can go stale, and there is no “demo data” to explain away. An empty account is empty: the app says so and offers the first session, rather than printing a scoreboard of zeros.

The workflow

StepWhat happensWhat it is built on
1. EnterContinue offline or sign in. The chosen account owns everything that follows.The auth seam and a per-account store
2. PickHome names the session to walk into: the soonest planned session in this week that is not behind the user.focusWorkoutThisWeek

4. FinishThe last tick closes the session; the summary reports volume, sets, reps and any record.SessionStats

How the technical choices support it

Provider, so a number has one owner

WorkoutProvider holds the account's sessions and exposes derived getters — the week's sessions, the streak, the session to walk into, the last time an exercise was trained. Screens watch the provider and read those getters; they never compute a shared figure themselves. This is the choice that made the week bug in Section 6 possible to find: two screens disagreeing meant two definitions existed, and the fix was to delete one and keep the other in the provider.

SQLite behind a repository, so memory survives the process

Every write goes through WorkoutRepository, which is constructed with a userId and cannot read or write a row without one. The in-memory copy is treated as a cache: it is loaded before the first frame, and writes are applied to it immediately and persisted behind it. A restart is therefore an ordinary event, not a data-loss risk.

An HTTP client behind a policy, so the network is an enhancement

The catalogue is loaded by ExerciseCatalog, which asks wger first and falls back to the bundled sets when the request fails, times out or returns nothing. Screens see one result type with a flag saying where it came from, so the offline case is a banner rather than an error screen.

Accounts without a server, so the demo works without wifi

Sign-in is local, behind an interface shaped like a server (AuthRepository). Passwords are hashed with PBKDF2-HMAC-SHA256 on a worker isolate, a sign-up answers either signed in or awaiting a confirmation link (the shape Supabase Auth returns), and the account card can change the password. A real backend could replace the implementation without a screen changing, and the project avoids shipping a Firebase configuration file in a public repository, which would be a credential in the APK.

Empty and error states as first-class screens

A new account, a failed request, an unknown session id and an invalid field all have a written answer. None of them is a blank screen and none is a fabricated value.

What the solution refuses to do

No cloud sync, no social features, no vitals or calorie tracking. These are recorded as deliberate cuts in the README, and the reasoning is the same in each case: a surface with nothing behind it is a promise the app cannot keep.

Section 05Goals and Objectives

Six objectives, each with the thing that would show it had been met. They are stated as outcomes rather than features because the project is graded on what the app can demonstrate, not on how much code it contains.

#ObjectiveEvidence that it was met
1 Make a session loggable in under a minute. The plan arrives with its sets, and each exercise shows what it was lifted at last time, so the user confirms rather than types. The logging screen's PREVIOUS column and “Last time” line are computed from the store; a session of eight exercises needs eight ticks.
2 Make every figure traceable. Any number on any screen can be recomputed from the sessions the user recorded. lib/data/session_stats.dart is the only place progress is computed, and its tests assert the counting rules directly.
3 Work without a network. Training and browsing the catalogue both survive a dead connection. The bundled catalogue renders behind an “offline catalogue” banner with a retry; the Discover screenshot in Section 3 is that path.
4 Support accounts without a server. Two people can use one device with separate training, and no credential ships in the app. Schema v4 gives every row an owner; switching accounts opens a different store and disposes the previous one; passwords are hashed, salted and iterated.
5 Be release-ready. Custom name, icon and splash; a working release APK; the steps written down. docs/BUILD.md, the generated launcher icon and splash, and the APK built from master.
6 Practise the engineering, not only the programming. Branches, reviewed pull requests, issues, tests, a DevTools case, and documentation a stranger can follow. More than thirty merged pull requests with inline review comments, ten issues closed, 293 tests, docs/DEVTOOLS.md.

Non-goals

The project did not aim to be a social product, a nutrition tracker or a cloud service. It also did not aim for visual parity with every frame in the design file: the design's sign-up flow has three steps, and the delivered screen collapses them into one because the app has no age column and no reader for it. That deviation is documented rather than hidden, which is the standard the rest of the project is held to.

What the screenshots exposed

Rendering every screen for this paper found two defects that code review had not, both of the same kind: a number that had been invented rather than derived.

The week disagreed with itself. Home read the length of the week's session list and the library counted finished sessions, so a week holding four plans and no training showed 4/4 on the dashboard and 0 of 4 sessions done in the library. The fix was to define the number once, next to the window it counts (sessionsDoneThisWeek), and have all three places read it.

The PREVIOUS column was a placeholder. The logging screen drew a “previous” column and a “No previous data” line from fields nothing ever wrote, so every exercise claimed to be new. It now asks the store for the completed sets of the last finished session containing that exercise — a feature that could not be tested before, because the fixtures named their exercises Push Day Movement 4 and no name ever repeated.

Both screenshots in Section 3 were rendered after the fix: the weekly tile and the library's week card read the same getter, and the logger's PREVIOUS column is filled from the store.

Section 07Technical Implementation

Three areas carry the course: navigation, state management and API integration. For each one this section states what the app needed, how it was built — naming the files and classes — and what would be harder or broken without it.

7.1 Navigation

What the app needed

Four kinds of movement: between the five destinations of the shell without rebuilding the app; from a list into a session, where the destination depends on an id; from a session into a logger and then a summary, without the user being able to walk back into a logger for a session that is already finished; and between entirely different windows when the user signs in or out.

How it was built

The destinations are an enum, and each value owns its route name, its label and its icon, so the shell, the navigation bar and the route table cannot fall out of step: 

enum AppTab { home, progress, workout, library, profile }

// lib/main.dart
for (final tab in AppTab.values) tab.routeName: (_) => AppShell(tab: tab),

Parameterised destinations are generated rather than registered, because a route like /workout-detail/:id is not a fixed string: 

static const String routeName = '/workout-detail';
static String routeFor(String id) => '$routeName/$id';

// resolved in PlusOneApp.routeFor, which reads the id off the settings
case WorkoutDetailScreen.routeName:
  return MaterialPageRoute(builder: (_) => WorkoutDetailScreen(route: settings));

Data is passed as an id, not as an object. The list pushes WorkoutDetailScreen.routeFor(workout.id); the detail screen reads the id from its route settings and asks the provider for the session (context.watch<WorkoutProvider>().byId(id)). That single decision is what keeps a detail screen alive across a change: when a set is ticked in the logger and the user walks back, the detail screen rebuilds from the provider rather than showing a copy of the session that no longer matches the store.

The last kind of movement is not a push at all. The gate in lib/main.dart chooses a window — splash while the session is being restored, the sign-in flow while signed out, the app while signed in — and each window carries a distinct ValueKey. Replacing the window instead of pushing onto it is what makes signing out leave no app screen on the back stack, and signing in as somebody else leave no store from the previous account listening.

What would be harder without it

Without the id-as-argument rule, a session would travel through constructors from the list to the logger to the summary, and every screen in the chain would hold a stale copy the moment a tick changed it. Without the window replacement, signing out would be a push, and the back button would walk into the account that just left.

7.2 State Management

What the app needed

Two kinds of shared state. Account state: is somebody signed in, who, and what is the app allowed to show. Training state: the sessions, the saved exercises, the profile, the weekly target, and every figure derived from them. Both are read by many screens and written by a few, which is exactly the shape provider exists for.

How it was built

ProviderHoldsRead by
AuthProvider The session, a status (checking, signedOut, signedIn) and a busy flag; commands to create an account, sign in, continue offline, sign out and delete. The gate in main.dart, the welcome and sign-in screens, the profile's account section.
WorkoutProvider Sessions, saved exercises, profile and metrics, plus derived getters: the week's sessions, the focus session, the streak, the count of finished sessions, the previous sets for an exercise. Home, progress, workout, library and profile — every tab.

Screens watch when they render a value and read when they only call a command. A tap handler that called watch would subscribe the screen to a rebuild it does not need; a build method that called read would never update. The distinction is small in code and large in behaviour, and it is applied consistently.

The store's lifetime is tied to the account, not to the app: 

// lib/main.dart — one store per account, created and disposed by the widget
ChangeNotifierProvider(
  key: ValueKey(userId),
  create: (_) => openStore(userId)..load(),
)

The key is what makes signing in as someone else open their training rather than reuse the previous object, and it disposes the departed store with the widget that held it. A widget test asserts both halves, including that the old store throws when a listener is added after the switch.

What would be harder without it

Without a shared provider, the weekly figure would have to be passed from the shell to each tab, and the "last time" lookup would be repeated in the logger and the summary. That is not a style preference: passing state down a constructor chain is how two screens end up computing the same figure differently — which is precisely the defect described in Section 6, where the dashboard and the library each had their own definition of the week. With a single provider and a single getter, the second definition cannot exist without deleting the first.

Without the account-keyed provider, the app would either keep one store for the process (leaking one account's training into another's) or dispose nothing (leaving listeners on a dead notifier).

7.3 API Integration

What the app needed

A catalogue of exercises the app does not have to invent, searchable by name and muscle, that still works when the phone has no signal in a basement gym.

The API and its endpoints

FORM reads the public wger REST API (https://wger.de/api/v2/) through package:http. Reads need no API key. 

GET https://wger.de/api/v2/exerciseinfo/?language=2&limit=60
Accept: application/json
timeout: 8 s

The catalogue holds 932 entries; the app requests the first page of sixty, which is more than a scrolling grid will reach in one session. Language 2 is English.

Sample response and parsing

A real response, abridged to the fields the app reads: 

{
  "count": 932,
  "results": [
    {
      "id": 9,
      "category": { "id": 10, "name": "Abs" },
      "muscles": [
        { "id": 11, "name": "Biceps femoris", "name_en": "Hamstrings" }
      ],
      "muscles_secondary": [
        { "id": 10, "name": "Quadriceps femoris", "name_en": "Quads" }
      ],
      "equipment": [ { "id": 10, "name": "Kettlebell" } ],
      "translations": [
        {
          "language": 2,
          "name": "2 Handed Kettlebell Swing",
          "description": "<p>Two Handed Russian Style Kettlebell swing</p>"
        }
      ]
    }
  ]
}

ExerciseApiClient._parse maps one entry onto LibraryExercise — the same model the bundled data sets parse into. It prefers the English translation and falls back to the first one, so a German-only entry still appears; it joins muscle names, preferring name_en over the Latin name; it flattens equipment objects to names; and it strips HTML from descriptions, because the card shows plain text. Entries with no usable translation are dropped rather than rendered blank.

Loading, success and error states

StateWhat the user seesTrigger
LoadingA progress indicator in the grid area; the header, search field and filter pills stay usable.The request is in flight.
Success (network)The catalogue, with the attribution line at the foot of the list.HTTP 200 with at least one parsable result.
FallbackThe bundled catalogue plus a banner: “Offline catalogue — wger.de couldn't be reached. Retry”.Timeout, socket error, non-200, invalid JSON, or an empty result list.
ErrorAn error state with a retry, only when both sources fail.The bundled assets cannot be read either.

Failures are collapsed into one ExerciseApiException at the client boundary, so no screen deals in socket errors or status codes. The policy — network first, bundled second, error only if both fail — lives in ExerciseCatalog.load, which is tested on its own with a fake client: a client that throws must produce a bundled result with isOffline true, and a client that returns an empty list must do the same.

What would be harder without it

Without the API, the catalogue would be whatever shipped in the assets — correct but frozen, and blind to exercises the user actually wants. Without the fallback, the library would be empty in the one place the app is used most. Without the collapse at the boundary, every screen with a catalogue would carry its own timeout handling and its own error copy, and they would drift.

7.4 Tests and verification

The suite holds 293 tests. Three of them are worth naming because they test the parts that would be expensive to get wrong:

  • The migration. A version-3 database is built by hand in the test — old tables, old primary keys, rows with no owner — and then opened by the current code. The test asserts that every row survived, that it belongs to the device account, and that the new primary key is (userId, id). Rewinding user_version on a current database would prove only that the migration runs.
  • The account switch. Signing in as somebody else must open their store and dispose the previous one. The test asserts the new store's contents and that adding a listener to the old store throws.
  • The counting rules. A planned session and an uncompleted set must not move any figure. The tests state that directly, which is how the weekly-goal defect in Section 6 became a failing test rather than an opinion.

dart format --set-exit-if-changed and flutter analyze are clean, and every commit in the history was required to be green on its own.

7.5 The DevTools case

The documented case is the release APK's size budget. Building with --analyze-size and opening the analysis in DevTools' App Size tool showed a 20 MB APK: 11.75 MB engine, 6.75 MB Dart AOT, 1.24 MB assets. Inside the AOT, package:plus_one — every screen, provider, repository and widget in the app — is 281 KB, while flutter_svg and its parser stack are ≈380 KB for five icons that total 1.1 KB on disk. The tool also confirmed that Material icons tree-shake from 1.6 MB to 4.8 KB, so the icon font is not the cost it is often assumed to be.

The decision was to keep flutter_svg — 1.9% of the APK, and replacing the icon pipeline would be a design change disguised as an optimisation — and to record it, with the order in which it would be cut if the budget ever mattered. docs/DEVTOOLS.md also documents the frame that a 12 000-iteration PBKDF2 verify blocked on the UI isolate (105 ms, measured), and why that work now runs through compute.
